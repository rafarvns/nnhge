# Events

> Status: **implemented** (event bus; [spec 001](../../specs/001-event-bus-and-scenes/spec.md)). API reference:
> [docs/api/events.md](../api/events.md). Engine input events: [docs/api/input.md](../api/input.md#events).
> Scenes are still being built.

## Why events

The game and the engine are made of parts that react to each other: a button press starts a jump, a
coin pickup updates the score and plays a sound, losing all lives opens the game-over scene. If each part
called the others directly, every part would know every other part. With an event bus, the part where
something happens **publishes** a fact, and every interested part **subscribes** to it. Adding a new
reaction means adding a subscriber; the publisher doesn't change (Open/Closed principle).

## Events vs. requests

| Kind | Meaning | Naming | Listeners | Example |
|------|---------|--------|-----------|---------|
| **Event** | Something that already happened | Past tense | Zero or many | `ButtonPressed`, `CoinCollected`, `SceneEntered` |
| **Request** | Something someone wants done | Imperative | Exactly one owner | `PlaySound`, `ChangeScene` |

Requests go on the bus only when the sender must not know the receiver (e.g. gameplay asking for a sound
without depending on the audio module). If you know the receiver, call its public API.

**Events are never used for queries.** "What is the player's health?" is a function call, not an event
round-trip.

## Event types

An event is a small, **trivially copyable struct** (no pointers to short-lived data, no `std::string`,
no virtual functions). Data is copied into the queue.

```cpp
struct CoinCollected {
    int value;
    nnh::Vec2 position;
};
```

Rules:
- Keep events small (aim ≤ 32 bytes). Large payloads → store the data elsewhere and send an id.
- One event type per meaning. Don't create a generic `GameEvent { int kind; ... }`.
- Engine events live in the public header of the module that publishes them
  (`ButtonPressed` in `<nnh/input.hpp>`). Game events live in the game's own headers.

## API

```cpp
nnh::Subscription sub = nnh::events::subscribe<CoinCollected>([](const CoinCollected& e) {
    score += e.value;
});                                    // unsubscribes automatically when `sub` is destroyed

nnh::events::publish(CoinCollected{10, pos});   // queued, delivered at the next dispatch point
```

- `subscribe<T>(handler)` returns an RAII `Subscription` (a `{slot, generation}` token). Destroying or
  resetting it unsubscribes. Scenes keep their subscriptions as members, so leaving a scene cleans up.
- `publish<T>(event)` **queues** the event. It is delivered when the engine dispatches, once per frame,
  after input is read and before the active scene updates.
- Handlers are small fixed-size callables (lambdas capturing `this` or pointers, up to 16 bytes; free
  functions; `subscribe<&Class::method>(object)`), stored inline without allocation.
- An immediate `emit<T>(event)` may be added later only if a spec justifies it; deferred delivery is the
  default because it keeps order deterministic.

## Dispatch rules

1. **One dispatch point per frame, single thread.** Events published during frame N (by the game) are
   delivered at the start of frame N+1, followed by the input events of frame N+1 (`ButtonPressed`,
   `ButtonReleased`, `TouchStarted`, `TouchEnded`), then the input actions' `ActionPressed`/`ActionReleased`
   ([actions](../api/actions.md), queued by the after-input hook of D32), then `SoundFinished`. Order is publish order
   (FIFO).
2. **Events published while dispatching** are appended to the same queue and delivered in the same
   dispatch, after the ones already queued. A **depth limit** (`events::kMaxDepth` = 8 levels of events
   generated by events) stops feedback loops; hitting it drops the event and logs a warning.
3. **A listener removed during dispatch is not called** afterwards, even for events already queued.
4. **A listener added during dispatch** receives events from the next publish onward. A listener added
   outside dispatch also receives the events still waiting in the queue.
5. **Listener order** for the same event type is subscription order. Don't depend on it for game logic;
   if order matters, publish a second event.

## Costs and limits (3DS)

- **No RTTI**: event type ids are compile-time (template static address), not `typeid`.
- **No per-frame heap allocation**: the queue is a fixed-capacity ring buffer of bytes; subscriber slots
  are fixed arrays. Capacities are set at `init()` (defaults 16 KB queue, 256 subscribers, configurable
  through `AppConfig`) and documented in `docs/api/events.md`.
- Overflowing the queue is a bug: it asserts in debug builds and drops + logs in release.
- Handlers should be short. Heavy work belongs in the scene's `update()`, triggered by a flag the handler sets.

## Pitfalls

- **Stale state**: when an event is delivered, the world may have changed since it was published
  (an entity in the event may be gone). Check ids before using them.
- **Global state**: the bus is shared. It is owned by the engine; game code accesses it only through
  `nnh::events`, never through its own globals.
- **Don't publish every frame** for continuous state (e.g. "button is held"); query instead.
