# Architecture decisions

Each decision has a short rationale. Change a decision by editing its row and adding a dated note below
the table; never silently. New decisions get the next number.

| # | Decision | Why |
|---|----------|-----|
| D1 | C++20 subset, no exceptions/RTTI in engine | Smaller binaries, predictable cost on the 268 MHz ARM11; still modern syntax. Same choice as Butano. See [../tech/cpp.md](../tech/cpp.md). |
| D2 | CMake + Ninja, presets, devkitPro's `3DS.cmake` toolchain | One build system for host and console, fast incremental builds, IDE support. See [../tech/cmake.md](../tech/cmake.md). |
| D3 | PC simulator is a host build on SDL3, not an emulator | Instant iteration and native debugging. Azahar and hardware stay as accuracy checks. |
| D4 | Simulator enforces 3DS limits (screen sizes, memory budget, texture rules) | Avoid "works on PC, breaks on console". |
| D5 | Rendering: 2D first on citro2d/citro3d; stereoscopic 3D later on citro3d | citro* are the maintained devkitPro GPU libraries; 2D gets games running sooner. |
| D6 | Assets compiled ahead of time into platform formats, packed in romfs (spec 007: per-file CMake build steps, incremental by timestamps; the C++ `assetc` with a content-hash cache waits for heavier conversions such as audio) | No decoding cost on the console; only changed assets rebuild. |
| D7 | Console builds always happen on the PC | The 3DS cannot compile in useful time. NNH Link *requests* builds and runs results. |
| D8 | NNH Link starts compatible with 3dslink, then adds its own protocol | Reuse a proven path (Homebrew Launcher netloader, stdio redirect on port 17491) before inventing. |
| D9 | `.3dsx` for the dev loop, `.cia` for installation | `.3dsx` is fastest to send and launch; `.cia` is the native installable artifact. |
| D10 | Tooling (`nnh` CLI, `assetc`) in C++ | One language for contributors, single static binary. Revisit if it slows us down. |
| D11 | **Event-driven: typed Event Bus (publish/subscribe) + Scenes (State pattern)** | Simple mental model, decoupled modules (OCP: add behaviour by subscribing), cheap on ARM11 when the bus is fixed-capacity and RTTI-free. ECS was considered and rejected for now: more abstract, harder for newcomers; can be added later as a module (2026-11-23: it is, as the optional `entities` module of D35; events and scenes stay how modules and scenes talk). See [events.md](events.md), [scenes.md](scenes.md). |
| D12 | **Spec-Driven Development + TDD** for every feature | Specs make intent reviewable before code and give Claude Code a precise contract; tests first keep core logic decoupled from hardware. See [../process/](../process/). |
| D13 | **Small files, one concept per file, module folders** | Easy to navigate for humans and AI tools, small diffs, fast incremental builds. See [project-structure.md](project-structure.md). |

| D14 | **Repository docs are the source of truth; the GitHub wiki is generated** (`scripts/docs_tool.py`, published by CI) | Docs are reviewed with the code in the same commit; the wiki gives readers navigation without a second copy that drifts. See [../process/documentation.md](../process/documentation.md). |
| D15 | **Portable core + one static library per system**, plugged in at link time through a documented platform contract, with conformance tests | Adding a system never touches core; no virtual cost on ARM11; consoles can't load libraries at runtime anyway. A runtime registry with virtual interfaces was rejected. See [platforms.md](platforms.md). |
| D16 | **System-only features via capability queries + extension headers** `<nnh/<system>/...>` | Games stay portable by default, unique hardware (stereo 3D, Joy-Con) stays reachable, and non-portable code is explicit at the include line. |
| D17 | **Core foundation before features**: time, logging, asserts/`Result`/crash report, memory accounting, debug overlay/profiler, confined `fs`; three build flavors (Debug, Development, Release) | Every later module needs them; a console without a debugger needs logs and crash reports from day one. See [foundation.md](foundation.md). |
| D18 | **Safe by default** (constitution X): confined file writes, atomic saves, fuzzed parsers, pinned supply chain, no telemetry | Homebrew has no sandbox; players' SD cards and saves must be safe. See [security.md](security.md). |
| D19 | **`IMAGES`: images embedded in the executable** (tex3ds `.t3x` on 3DS, PNG on PC), loaded by name — kept for small games; since spec 007 `ASSETS` (romfs, on demand) is the recommended way and `load_texture` looks there first | Games got graphics before the asset pipeline existed; the same `load_texture` call works for both. |
| D20 | **Rendering is recorded, then submitted per screen in passes; one texture type for 2D and 3D** (3DS: `C3D_Tex` drawn by citro2d; PC: SDL renderer on an `SDL_GPUDevice`, default renderer as headless fallback). **Amended by D41**: the PC's 3D pass is drawn by the engine's CPU rasteriser, not on the GPU device | Layers, batching and stereo (one list, two eyes) come for free, and 3D (M8) slots in as a pass without changing 2D calls or textures. See [rendering.md](rendering.md). |
| D21 | **Audio: the platform plays voices, core owns the rules** (spec 008). The contract is samples + voices (gain per speaker, rate, loop, pause); priorities, groups, pan, pitch, fades, loop points and Ogg decoding (vendored stb_vorbis) are core logic. Without output, core runs the same rules silently, ending voices by the clock | The 3DS DSP mixes 24 channels in hardware for free; mixing in core would cost the Old 3DS CPU. Rules in core are the same everywhere and unit-tested on the fake platform. See [api/audio.md](../api/audio.md). |
| D22 | **Packaging is a build step around devkitPro's** (spec 009): one identity in `nnh_add_game()` (title, author, version, icon) feeds the `.3dsx` SMDH, the `.cia` and the PC window; the `.cia` is made by makerom from the same ELF, SMDH and assets, with our own RSF and a bannertool banner; the tools are pinned prebuilt releases fetched by the first `.cia` build | A contributor needs nothing new until a game asks for a `.cia`, and the game behaves the same in both formats. See [guides/packaging.md](../guides/packaging.md). |
| D23 | **`nnh` speaks the netloader and FBI protocols itself** (spec 010): its own small C++ code sends `.3dsx` files to the Homebrew Launcher (zlib stored blocks, chunks of at most 16 KB, argv[0] = `sdmc:/3ds/<name>`), receives the game's log on TCP 17491 and serves `.cia` files to FBI; discovery asks every local network's broadcast | No dependency on devkitPro's `3dslink` or Python, works on Linux and in CI, and NNH Link (spec 011) reuses the same code. D8 still holds: it is compatible with 3dslink. See [guides/nnh-tool.md](../guides/nnh-tool.md). |
| D24 | **One link library, mutual authentication, no encryption** (spec 011): `link/` (`nnh_link`) is built for PC and 3DS and holds sockets, SHA-256/HMAC, the message codec, pairing and the sessions, so `nnh serve` and NNH Link run the same code. A 6-digit code pairs a console with a PC once; every connection then proves both sides with HMAC (the server first) and every message carries a MAC and a sequence number; nothing is encrypted. Launching uses Luma3DS's `hb:ldr`, like the Homebrew Launcher | Our own small code (no third-party crypto), tested with published vectors and fuzzed. A console runs programs only from the PC it paired with, a PC builds only for paired consoles. Known limit: someone recording the network *while pairing* could brute-force the code offline: pair on a network you trust. See [guides/nnh-link.md](../guides/nnh-link.md). |
| D25 | **Game features are opt-in libraries over the core, code first** (constitution XI): tilemaps, collision, tags, data assets, prefabs, animation, UI and the rest of M7 are separate modules a game may use, skip or replace; none needs another the game didn't choose; every one works through the C++ API, and files (hand-written text, Tiled, Aseprite) are converted at build time | Godot/Unity productivity without their lock-in: NNHGE has no editor, and a programmer who prefers their own entities, maps or data loses nothing and pays nothing for the features they skip. |
| D26 | **tile layers are drawn as tile batches**: one draw-list command per (map layer, tileset), sorted with sprites by layer; at submit core expands only the visible cells into 10-byte quads and calls one contract function, `draw_tiles`, per batch (between `draw_2d` calls). Tile quads per frame are capped by `AppConfig::gfx.max_tiles` on every system. **Confirmed** (spec 012, Old 3DS XL): 4 full 16×16 layers + 300 sprites at 60 Hz (avg 16.7 ms, worst 17.4 ms), limits 6 layers or 600 sprites; no fallback needed. **Amended by D33** (zoom: a destination tile size per batch, snapped tile edges, row chunks at zoom < 1) | Tiles as sprites would cost ~12 µs each on an Old 3DS (a full 16×16 layer is up to 416 tiles); pre-rendered chunks need ~1.5 MB of VRAM per layer and stall when scrolling or editing tiles. Batches skip the per-tile record, sort and texture lookup, keep layers, cameras, parallax, flips and animated tiles exact, and need one small contract function. See [rendering.md](rendering.md), [plan 012](../../specs/012-tilemaps-and-collision/plan.md). |
| D27 | **build-time conversions that CMake scripts can't do run in `nnh-assetc`**, a host C++ tool (`tools/assetc/`), first for Tiled maps: a target in PC presets, built for the host with `ExternalProject` in cross presets (or `-DNNH_ASSETC=<path>`), only when a game needs it; one step per file with a Ninja depfile (paths relative to the step's working directory, so MSYS's CMake reads them too). **Confirmed** by spec 012 (Tiled maps): a map edit reconverts only that map (0.2 s for the example's level), and a 3DS build without maps never builds it | Fulfils D6/D10's `assetc`. CMake's JSON access is quadratic and it can't write binary files; Python would be a new dependency for every game. Sharing the format and validator with core means the build checks maps with the console's own code. |
| D28 | **The PC drives a Development game over the game's own log connection**: `nnh` sends fixed 16-byte messages stamped with the frame they apply to (buttons, sticks, touch, screenshot, hello/bye); the game answers with in-band records (`0x1E 'N' 'R'` + type + length) in its log stream (ticks, screenshots, late/rejected). Core merges remote input into the frame's sample before input is read; platforms only move bytes and read their screens back. The simulator connects to `nnh` on the loopback interface (`NNH_REMOTE`). Debug/Development only; Release has no code for it | One connection the console opens to the PC that launched it: no new port, and log lines and records stay in order (frame-exact `expect`). Fixed-size messages are bounded and fuzzed without heap; `nnh_link`'s codec allocates per message, needs a pairing secret and isn't a game dependency. Frame stamps make scripts repeatable; the same session code serves console and simulator. See [plan 013](../../specs/013-console-remote/plan.md). |
| D29 | **Data assets: the schema is C++, read by the build through a per-game host program; text is converted to a layout-independent binary** (spec 014). `NNH_DATA_TYPE`/`STRUCT`/`ENUM`/`FIELD` tables (member offsets, kinds deduced by templates, types identified by the address of an inline variable, registered by static nodes; no RTTI) are compiled into the game and into `<game>_data_schema`, a host program not linked against the engine (PC: the same objects; cross presets: an `ExternalProject` rebuilt only when the console's schema objects change) that writes a text schema description. The generic `nnh-assetc data` checks each TOML-subset file against it and writes it field by field with a schema fingerprint; `nnh-assetc data-index` checks references (32-bit path hashes), names and collisions and writes `.nnh_data`; core validates every file with the same validator and loads it into the game's struct | One source of truth checked by the compiler, with defaults from the struct itself; `nnh-assetc` stays generic and prebuildable (D27); the console never parses text or floats; a field-by-field format makes host and console layouts irrelevant; per-file steps keep data edits free of C++ compiles (constitution III). Rejected: a schema file with generated C++, parsing C++ headers, a schema section read back from the linked executable, TOML at run time. See [plan 014](../../specs/014-data-assets/plan.md). |
| D30 | **Scenes carry an intrusive list of attachments** (spec 015). `Scene` holds one pointer, `detail::SceneAttachment* attachments_`. A node is `{next, notify function pointer, epoch}` and lives inside the module object that attaches it (first user: a `TweenSet` bound to a scene, node in its heap block). The scene stack notifies the top scene's attachments `BeforeUpdate` right before its `update()`, and every attachment of a scene `AfterExit` right after its `on_exit()` (pop, replace, end of `run()`, `shutdown()`). Nodes attached during a pass wait for the next one; detaching during a pass is safe (cursor). The `Scene` destructor checks that the list is empty | Bound sets update only while their scene is on top (a pause menu freezes the level) and are cleared before anything can call back into a scene that has left, with no allocation, no `virtual`, and a cost of one pointer and a null check for scenes that bind nothing. The scene module never names the tween module (dependencies point down; XI). Rejected: making the game call `update()`/`clear()` by hand (the bug the spec removes), a `virtual` hook on `Scene` (scenes would depend on tweens, one set per scene), a global scene→set registry (capacity, lookups, hidden state), a `TweenScene` base class (forces inheritance), scene events (delivered a frame late, can't express "before update"). See [plan 015](../../specs/015-tweens-and-timers/plan.md). |
| D31 | **Sprite animation: Aseprite exports are converted at build time into the library's own block format** (spec 016). A sprite library (frames, clips, markers, state machine) is one block whose layout is the `.nnhsprite` file, as `.nnhmap` is for maps, so code-built and loaded libraries are the same data and the console validates files with the converter's own validator. The suffix `<name>.ase.json` (an Aseprite JSON export beside `<name>.png`) is reserved and owned by the `nnh-assetc sprite` step, which writes `<name>.nnhsprite`; the PNG stays the texture at the same path. Editor files `.ase`/`.aseprite` are not packed. This step comes before every generic rule, including D29's data routing: `.ase.json`, `.ase` and `.aseprite` are pipeline-owned, and `nnhsprite`, `ase`, `aseprite` are not data keys. Markers come from tags named `@name`. Animators report markers, loops, finishes and state changes inside their owner's update (inline callback + the update's returned view), never as engine bus events | Artists export a JSON every tool can read; the build checks timings and names with `file:line` errors; the console never parses JSON. A suffix keeps the game's own `.json` files untouched (sniffing every `.json` would make them build errors). Reading `.aseprite` binaries was rejected (paid tool, larger parser surface). The frame clock (`Frames`, `FrameTime`) lives in `<nnh/time.hpp>`, so animation doesn't depend on tweens (XI). See [plan 016](../../specs/016-sprite-animation/plan.md). |
| D32 | **Input actions are evaluated by an after-input hook list in the frame loop, and player bindings are saved as overrides** (spec 017). `app.cpp` holds one function pointer, set while an intrusive list of `detail::InputHook` nodes `{next, run function pointer}` (`core/input_hooks.*`, linked only by its users) is not empty; `nnh::frame()` calls it right after the frame's input events are queued (the sample is final: remote input merged, D28; D-Pad mirror applied) and before audio and dispatch. Each `ActionSet` keeps its node in its heap block, added at creation (sets run in creation order) and removed at destruction. A set reads the public input queries, queues `ActionPressed`/`ActionReleased` after the frame's button and touch events, and enables a scene-bound context exactly when `scenes::top()` is its scene; a D30 attachment per bound context only ends the binding after the scene's `on_exit()` (a binding lasts one stay on the stack). Saved bindings are an `NNHB` blob: a 16-byte header (format version, entry count, the game's bindings version, CRC-32) and 12-byte entries keyed by action-name FNV-1a hash, slot and part, at most one per changed remappable slot (≤ 3088 bytes), written through `nnh::save` or into a caller buffer, validated whole before anything changes, with unfitting entries skipped and counted; fuzzed | Action events arrive in the same frame as `ButtonPressed` and queries are fresh in `update()`, with nothing for the game to call; neither `app` nor `input` names the actions module (dependencies point down, XI), nothing allocates, and a game without sets pays one null check. Checking the top scene at evaluation has no one-frame overlap after a push (D30's `BeforeUpdate` comes after the evaluation). Overrides keyed by name hash survive enum reorders, new actions and new defaults. Rejected: a game-called `update()` (events a frame late, easy to forget), a call from `input_update()` (input would depend on an optional module), subscribing to `ButtonPressed` (delivered at dispatch, a frame late; no stick or touch events), a single function-pointer slot (one user only), weak symbols (toolchain-dependent), saving full bindings (new defaults lost), a text format (a parser on the console). See [plan 017](../../specs/017-input-actions/plan.md). |
| D33 | **`Camera2D` has a zoom, applied by core when it builds a screen's pass; tile batches carry a destination tile size** (spec 018). A camera-relative draw lands at `(world − position) × zoom` (`position` stays the world point at the screen's top-left; zoom 0.5–4, clamped by `set_camera`); `ignore_camera` draws and the debug pass are never zoomed. Sprites, glyphs, rectangles and lines need no contract change (`DrawItem2D` is already in screen pixels; outlines and lines stay one pixel thick). For tiles (amending D26) core snaps each tile's **edges**, `edge(i) = O + round(i × tile × zoom)` from the layer's snapped origin, so tiles never gap or overlap: `TileBatch2D` gains `dst_w`/`dst_h` (`floor(tile × zoom)`) and `TileQuad2D` (still 10 bytes) two orientation bits, "one pixel wider/taller". Visible cells follow the zoomed view; a batch larger than the 1600-quad scratch is expanded and sent in row chunks. At zoom 1 the quads, batches and items are today's bytes (pinned by a regression test) | Hand-written cameras zoom too (constitution XI), PC and 3DS place every zoomed draw on the same pixels because core computes them, integer zooms are pixel-exact, and the fake platform sees the zoom in recorded data. Rejected: GPU view transforms (`C2D_ViewScale`, `SDL_SetRenderScale`: seams at fractional zooms, per-GPU rounding, invisible to tests), a 16-bit size per quad (+40 % scratch), a batch-level float scale rounded by each platform (the seam rule written per platform), zoom only in the camera helper (sprites unscaled), a 4× scratch (+48 KB for every tilemap game). See [plan 018](../../specs/018-camera-helpers/plan.md). |
| D34 | **Collision layers live beside the map, not in `Grid`; queries read the game's memory through strided views and decide with exact predicates** (spec 019). `collision::Layers` is a plain 32-bit value and detection is one-directional (`mask & layers`). `collision::Grid`, its callback signature and the `.nnhmap` format (version 1) don't change: a map block gains a **runtime area after its format bytes** (at `header.file_size`) holding a layer set per tile layer and per tile id (default: the default layer) and 8 grid-mask slots. `collision_grid()` keeps returning today's grid (same callback, same context; `map_collision.cpp` is not edited), `collision_grid(mask)` returns a grid whose context is that mask's slot and whose callback tests the mask once per contribution. Tiled's `collision_layers` (an int, e.g. a flag enum saved as a number) stays a property and is read at load. Queries take a `BoxView` (address of the first box, count, byte stride, optional layer address and stride), never a copy; the grid traversal (Amanatides & Woo) and the slab tests decide order, corners and ties with cross products in `double` computed from the float inputs (exact for coordinates on a 1/256-pixel lattice within ±2^17 px), and round each reported value once to `float`; the distance alone uses the IEEE square root (`-fno-math-errno`, inlined) | Game grids and every existing caller run the same code at the same cost, maps converted before keep loading byte for byte, a layered map costs 132 bytes plus 4 per tile id instead of 4 per cell, and the game's structs stay as they are. Exact predicates make "no corner leak" and "touching is not hitting" hold exactly for any ray length, and a brute-force integer reference can check the traversal cell for cell; IEEE `double` is as deterministic on the 3DS (VFPv2) as on the PC. Rejected: a mask field in `Grid` (the callback can't see it without a new signature, which breaks every game's callback, or a second callback pointer and one more branch in every lookup), a per-cell layer array (up to 16 MiB), a format version 2 with a new section (the header's offset table is full; every map would need reconverting), copying boxes into an engine container, a callback per box, a float DDA with accumulated `tMax` (corner decisions drift with the ray's length). See [plan 019](../../specs/019-collision-layers-and-queries/plan.md). |
| D35 | **Entities and pools: stable slots per component kind, 32-bit generational handles, slots quarantined until a flush** (spec 020). Two optional modules (D25, XI): `<nnh/pool.hpp>` (`Pool<T, N>` with inline storage, `Pool<T>` in one tagged block) and `<nnh/entities.hpp>` (`World` in one tagged block). This is D11's "ECS later, as a module": it is a data store a game may use, not the engine's architecture — events and scenes stay how modules and scenes talk, and the engine publishes no lifecycle events. A handle is a `uint32`: slot (16 bits) and generation (16 bits), 0 = null; each slot's meta word holds its generation and a live flag, so a lookup is one compare. A component kind is the game's plain struct, identified by `detail::type_id<T>()` (never ordered) and stored in its own fixed array (+ owner, live/quarantine/fresh/removing bitmaps); an entity is a record (meta, kinds mask, tags, a slot per kind). Nothing moves: free and quarantined slots hold a constructed `T{}`. Acquire/spawn/add take the **lowest free** slot; release/destroy/remove make the handle stale at once and quarantine the slot until `flush()`; iterations visit ascending slots (`each<A, B...>` by the first kind's slots) and skip slots created during them. `destroy` runs per-kind remove hooks (registration order, data intact), then resets; destroys requested by hooks are queued (FIFO, no recursion). Tags are FNV-1a 32 hashes (`detail::fnv1a32`), up to 8 per entity, found by scanning records. A pool or world bound to a scene uses D30 unchanged: `BeforeUpdate` flushes, `AfterExit` clears (hooks run; spawns are refused while clearing) | Stable addresses keep tween pointer targets, animator callbacks and box views (spec 019) valid and let views read components in place; lowest-free reuse and slot-order iteration make handles and orders identical on PC and 3DS and keep the platformer's "first inactive bullet"; quarantine means no object of the same frame takes a released one's place; 32-bit handles fit events and structs, and the wrap limit (a handle kept across 65 535 reuses of its slot, ≥ 18 min at one flush per frame) is documented. Fixed capacities and one block keep memory known (≈ 68 KB for 1024 entities × 8 kinds × 4 tags besides components). Rejected: archetypes (components move, per-combination tables), packed sparse sets with swap-and-pop (components move, order follows removal history), kind-major sparse arrays (two cache lines per lookup), a FIFO free list, immediate reuse, 64-bit handles, bus events for spawns and destroys (stale by delivery), a per-game component enum, a new scene notification. See [plan 020](../../specs/020-entities/plan.md). |
| D36 | **Prefabs: a library of flattened prototypes, spawned through an all-or-nothing reservation inside the world** (spec 021; implemented 2026-11-23, Old 3DS run pending). An optional module (D25, XI), `<nnh/prefabs.hpp>` over `<nnh/entities.hpp>` (the Prototype pattern). A `PrefabLibrary` is one tagged block sized at creation (prefabs ≤ 1024, component entries, value bytes): per prefab a record (its entry range, up to 8 tags, a placement member as kind + byte offset + `Vec2`/`Rect`, its own spawn hook and a link to its bases' hook chain), per entry a type id, a value offset and copy/destroy function pointers, and the values (copies of the game's structs). Names are FNV-1a 32 hashes in a separate array and an open-addressing table; a duplicate hash is refused, so two names of one library never collide silently; `find` returns a `Prefab` handle (index + the library's stamp) and spawns take handles. Variants are flattened at registration (the base's entries replaced in place or appended, tags united, hooks chained base first; unreplaced entries share the base's stored values). A spawn makes **one** entities-internal call that takes all of an entity slot, one slot per kind and the tags with exactly `spawn()`/`add()`'s bookkeeping — or nothing, counting the refusal as they would — then copy-constructs each value (or the copy's override) into its slot, writes the placement and runs the hooks: the bytes of hand-written `spawn`/`add<T>(e, value)`/`add_tag` calls in that order. A full capacity asserts (default) or is a quiet miss (`WhenFull::Miss`, per library). Map objects name a prefab by their `prefab` string property, else by type; only one source file includes the tilemap header. No events; a spawned entity keeps no link to its prefab | A name declared once replaces a spawn function and a `strcmp` branch per kind, and lets designers place new things in Tiled; flattening makes a variant cost what any prefab costs; the reservation gives all-or-nothing spawns without widening spec 020's public API (spec 020's public header is unchanged: the additions live in `src/entities/entities_internal.hpp`) and costs one call per spawn instead of one per component and tag; shared bookkeeping code keeps prefab spawns equal to hand-written ones, so replays and goldens don't move. Rejected: a global registry with static registration (a hidden global; data assets aren't loaded yet), a live `IsA` link resolved per spawn, public `World::can_add`/`add_bytes`, check-then-spawn through public calls (three passes), a record scan for `find` (memory-bound on the Old 3DS), names stored in Release, a prefab file format, an automatic tag or component naming the prefab. See [plan 021](../../specs/021-prefabs/plan.md). |
| D37 | **Transforms are values with deterministic math; the hierarchy is one engine component kind in the game's world, computed by an explicit pass** (spec 022; implemented 2026-11-24, pre-approved overnight 2026-11-23). Two optional modules (D25, XI). `<nnh/transform.hpp>` (only `<nnh/math.hpp>`, declarations only): a local `Transform2D` (position, rotation in radians clockwise, scale; negative = mirror) and a `WorldTransform2D` = an affine map (axes and origin: points exact under any chain, shear included) plus drawing values (accumulated rotation, product of scales: exact without shear, Unity's lossy approximation with it); every float operation in core sources with `-ffp-contract=off`, signs and finiteness tested on bits; sine and cosine by spec 015's libm-free polynomial (moved to `src/core/`, bits unchanged) after a reduction to the nearest quarter turn that snaps tiny remainders, so the engine's quarter-turn constants give exact 0/±1, and every edge case (NaN, huge angles) has defined bits. `<nnh/hierarchy.hpp>` over `<nnh/entities.hpp>`: `nnh::Node` (80 bytes: links as node slots — parent, first child, siblings with the first child's previous = the last child —, depth, the local, a sine cache keyed by the rotation's bits, the stored world) is registered by the game with `node_component(capacity[, hook])`; a `Hierarchy` view does everything. `propagate()` computes every world: roots in ascending node slots, each subtree depth-first in attach order through parent links (no stack, no game code, prefetched); `world_now(e)` gives the same bits fresh. Stored worlds are computed at construction, keep-local attach, tree spawns and the pass; keep-world reparenting keeps the stored world and derives the local from the stored worlds (Bevy's `set_parent_in_place`). Destroying a node destroys its subtree through spec 020's destroy queue (the engine's remove hook, after the game's: breadth-first, hooks with data intact, parents stale); removing the node component makes the children roots that keep their worlds. Prefabs may have up to 8 child entries per prefab (≤ 32 entities per spawn), spawned all or nothing through an entities-internal reservation of N entities, hooks children first; the tree code is linked only through `nnh::child()`. | D47 | **Textures and meshes are freed only after the platform waited for the GPU** (spec 026a, 2026-11-25, found while trying a CPU/GPU overlap that was dropped: plan 026 "CPU/GPU overlap tried (D47) and budgets set"). `platform::end_frame()` may return with the GPU still drawing (the 3DS's `C3D_FrameEnd` only starts it); the next `begin_frame()` waits for it. ## NNH Link (D7, D8, D24)

```
 console (NNH Link)                          PC (`nnh serve`)
 discover servers (UDP 17492 broadcast) ───>  answers: id + name
 pair once (6-digit code), then every
 connection: mutual HMAC proofs         <──>  (TCP 17492, every message MAC'd)
 list games                             ───>  the repository's games (nnh_add_game)
 build <game> [release]                 ───>  cmake --build (incremental)
                                        <───  build output lines, then the .3dsx (+ SHA-256)
 save to sdmc:/3ds/nnh/, start it through Luma3DS's hb:ldr with --nnh-return=<Link>
 game stdout/stderr                     ───>  shown in the terminal (TCP 17491, 3dslink-style)
 the game exits → NNH Link starts again
```

Built in [spec 011](../../specs/011-nnh-link/plan.md); guide: [guides/nnh-link.md](../guides/nnh-link.md).
Still open: installing `.cia` files from Link (needs AM service access) and Link itself as a `.cia`.

## Future platforms

Switch (libnx + deko3d), Wii U (wut). A platform is accepted when every example builds and runs on it.

never through `#ifdef` in game code.
