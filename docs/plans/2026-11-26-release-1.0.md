# Plan · NNHGE 1.0 release (game projects, `nnh new`/`nnh doctor`, versioning, release) · nnhge

Date: 2026-11-26 · Status: draft (Xatu; nothing here is approved, every item becomes a spec first)

Written in English like every repository doc. The maintainer's report is in Portuguese.

## Goal

A newcomer downloads one release of NNHGE, installs the tools, runs `nnh doctor`, `nnh new mygame`, `nnh run mygame --pc`
and `nnh run mygame` and has their own game running in the simulator and on a 3DS, in a folder outside the engine
repository, on Windows and Linux.

Done when:
- a GitHub release `v1.0.0` exists with a source archive, prebuilt `nnh` for Windows x64 and Linux x64, the examples as
  `.3dsx` (and one `.cia`), `SHA256SUMS` and release notes from `CHANGELOG.md`;
- on a clean Windows machine (Windows Sandbox) and a clean Linux machine, following only the README and the guides, a
  project made with `nnh new` builds and runs in the simulator and on the maintainer's Old 3DS XL, and its generated
  test script passes (`nnh run mygame --pc --script tests/smoke.nnhs` → exit 0);
- the 1.0 API promise (what is stable, what is not) is written down and the release checklist was followed and
  ticked for that tag.

Non-goals:
- shipping, installing or repackaging devkitPro (its trademark policy forbids calling a repackaged toolchain
  devkitPro; we point to the official installer and `dkp-pacman`);
- an installed CMake package with prebuilt engine libraries (`find_package(nnhge)`), package managers (winget, Scoop,
  Homebrew, AUR), code signing of `nnh`;
- `nnh setup` that installs system tools (deferred; see decision 4);
- macOS as a supported host for 1.0 (best effort, see decision 5); New 3DS checks (the maintainer has only an Old 3DS);
- an editor, more than one project template, upgrading a project between engine versions automatically;
- M9 (3DS hardware features) and everything in the ROADMAP's "Later".

## Current state (studied)

- **1.0 scope.** UI (028), fonts/localization (029) and live values (030) are merged; 030's console bench budgets are
  still pending; 031 (hot reload of assets) is approved with its plan and tasks and is next to implement. Evidence:
  `specs/README.md` rows 028–031; `git log` top `3547b64 Merge spec 030`. The README already promises "a `nnh new` /
  `nnh doctor` CLI to start a project in a few commands" (`README.md:19-21`). ROADMAP "After 1.0" item 1 is the first
  release plus a small sample game built from scratch (`docs/ROADMAP.md:382-386`).
- **Games only live inside the engine repository today.** `docs/guides/getting-started.md:66-82` tells the user to add a
  folder and `add_subdirectory` it from the top-level `CMakeLists.txt`; "a standalone project template (engine as a
  dependency) comes with the `nnh` CLI". Spec 010 lists "a standalone project template (`nnh new`) and using the
  engine outside this repository" as a non-goal (`specs/010-nnh-cli-run/spec.md`, Non-goals).
- **`nnh` refuses to work outside the engine repository.** `find_repo_root` requires `CMakePresets.json` **and**
  `engine/core` (`tools/nnh/src/repo.cpp:20`); `build_target` prints "run it inside the NNHGE repository"
  (`tools/nnh/src/commands/build.cpp:69-71`). Builds, logs and the games manifest are found under
  `<root>/build/<preset>/` (`build.cpp:51,60`; `repo.cpp:122`), so a game project that keeps the same `build/<preset>`
  layout fits the tool once the root detection changes.
- **The CMake helpers are not safe to call from another project yet (strong hypothesis, to confirm in step 1).**
  `nnh_add_game()` and its helpers read directory-scoped variables set when the engine's files were included:
  `_NNH_GAME_CMAKE_DIR` (`cmake/nnh_game.cmake:35`), `_NNH_ASSETS_DIR` (`nnh_assets.cmake:43`), `_NNH_CIA_DIR`
  (`nnh_cia.cmake:11`), `_NNH_CTR_TOOLS_DIR` (`nnh_ctr_tools.cmake:9`), `_NNH_DATA_ROOT` (`nnh_data.cmake:31`),
  `_NNH_IMAGES_DIR` (`nnh_images.cmake:11`), `_NNH_PACKAGE_ART` (`nnh_package_rules.cmake:17`), and `NNH_PLATFORM`,
  a normal variable set in the engine's top-level scope (`CMakeLists.txt:11-15`) and tested inside `nnh_add_game`
  (`nnh_game.cmake:118`). CMake functions are global but read variables from the **caller's** scope, so a game that
  `add_subdirectory()`s the engine and then calls `nnh_add_game()` from its own directory would see them empty.
- **The engine builds everything when it is a subproject.** `NNH_BUILD_EXAMPLES` and `NNH_BUILD_TESTS` default to ON
  (`CMakeLists.txt:27-32`); `apps/` (NNH Link) and, in PC presets, `tools/nnh` are always added (`CMakeLists.txt:59-65`).
  Nothing uses `PROJECT_IS_TOP_LEVEL` yet except `tools/assetc/CMakeLists.txt:150` and
  `tools/data_schema/CMakeLists.txt:39`. Internal paths use `PROJECT_SOURCE_DIR` (`cmake/nnh_host_tools.cmake:49,80`,
  `tools/nnh/CMakeLists.txt:46-63`), which is right when the engine calls `project(nnhge)` itself.
- **Presets.** Six configure presets (`pc-*`, `3ds-*`; flavours Debug/RelWithDebInfo/Release), Ninja,
  `binaryDir ${sourceDir}/build/${presetName}`, 3DS toolchain `$env{DEVKITPRO}/cmake/3DS.cmake`, presets version 6,
  CMake ≥ 3.25 (`CMakePresets.json`). `nnh` picks `pc-dev`/`3ds-dev` or `-release` (`repo.cpp:30-31`) and
  `NNH_PRESET` overrides (`repo.cpp:125-131`).
- **3DS builds on Windows** run through devkitPro's MSYS2 bash (`repo.cpp:52-71`, default `C:/devkitPro/msys2`,
  `DEVKITPRO_MSYS2` overrides). `scripts/dkp.sh` also passes the host compiler as `NNH_HOST_CXX`, which host tools
  (`nnh-assetc`, data schema programs) need in cross presets (`scripts/dkp.sh:22-36`,
  `cmake/nnh_host_tools.cmake:19-22`); **`nnh` does not pass `NNH_HOST_CXX`** (grep: no match in `tools/nnh`). A
  first `nnh build` of a 3DS game with maps, data or fonts, configured by `nnh` rather than `dkp.sh`, may then fail to
  find a host compiler (hypothesis, to confirm in step 1).
- **SDL3** is found on the system, else the official prebuilt MinGW/MSVC package, else built from source (Linux/macOS),
  pinned 3.4.20 by SHA-256, downloaded into the build folder (`cmake/nnh_sdl3.cmake`). makerom v0.19.0 and bannertool
  1.2.3 are fetched pinned on the first `.cia` build (`cmake/nnh_fetch_ctr_tools.cmake:6-15`). Windows CMake builds
  without CA certificates reuse Git for Windows' bundle (`nnh_sdl3.cmake:17-28`).
- **`nnh` is standalone.** No SDL; links `nnh_link`, threads and a few pure core files; statically linked on MinGW
  (`tools/nnh/CMakeLists.txt:64-80`). Commands today: `build`, `run`, `install`, `serve`, `unpair`, `help`
  (`tools/nnh/src/cli.cpp:5-31`); no `--version`. Its test binary `nnh_tool_tests` and a simulator end-to-end script test
  exist (`tools/nnh/CMakeLists.txt:82-130`). A file-embedding helper exists (`cmake/nnh_embed.cmake`), usable for
  project templates.
- **The game↔tool protocol is versioned and strict**: the hello message carries `kVersion` and a mismatch is refused
  (`engine/core/src/remote/remote_wire.cpp:62-64`). So `nnh` and the engine a game was built with must agree.
- **Version.** `project(nnhge VERSION 0.1.0)` (`CMakeLists.txt:3`); no version header in `engine/core/include/nnh/`;
  no git tags (`git tag` empty); no CHANGELOG; no GitHub release (`gh repo view`: `latestRelease: null`).
- **Public surface.** 45 headers in `engine/core/include/nnh/`, a `nnh/detail/` folder (`handle.hpp`,
  `pool_core.hpp`, `world_layout.hpp`, …), platform contract headers in `engine/core/contract/nnh/platform/`, 3DS
  extension headers `nnh/3ds/{console,launch,network}.hpp`. `docs/tech/cmake.md` already calls
  `nnh::detail::kThreeDsLayout` an internal helper.
- **CI.** `.github/workflows/ci.yml` is `workflow_dispatch` only ("to save Actions minutes", `docs/tech/cmake.md:292-296`):
  docs, pc-linux, nintendo-3ds in `devkitpro/devkitarm:latest` (not pinned by digest), fuzz. `wiki.yml` runs on push
  to `main`. Actions are pinned by commit SHA. **The repository is public** (`gh repo view`: `PUBLIC`), and GitHub
  does not charge standard hosted runners for public repositories, macOS included (source below), so a manual release
  workflow costs nothing.
- **Linux checks** run on the homelab build VM 120 (Ubuntu 24.04, GCC 13/14, clang 18, devkitPro extracted from the
  official image because `*.devkitpro.org` answers 403 to the maintainer's IP; CLAUDE.md "Build", `docs/tech/cmake.md`).
- **Console test scripts** exist for almost every example (`examples/*/tests/*.nnhs`: 31 scripts, one or more per
  example), so a release console pass is "press Y per script".
- **Sizes.** Tracked sources: engine 2.9 MB, tools 1.1 MB, third_party 0.7 MB, cmake 0.15 MB, link 0.13 MB (engine-only
  ≈ 5 MB uncompressed); examples 2.3 MB, tests 3.6 MB, specs 3.4 MB, docs 1.1 MB; 3053 files
  (`git ls-files … | wc -c`). A full source archive is a few MB compressed.
- **Licences.** Engine zlib (`LICENSE`); vendored `stb_vorbis`, `stb_truetype`, `stb_image` (MIT or public domain),
  Ryu (BSL-1.0) listed in `docs/tech/third-party.md`. The localization example ships an OFL font with its licence
  (`examples/localization/assets/licences/OFL-NNHExampleSansJP.txt`); the example sounds have no recorded provenance
  file (to audit before shipping example binaries).
- **Maintainer's machine:** CMake 4.4.2, Ninja 1.13.2, WinLibs GCC 16.2.0; `E:` has **13 GB free (95% used)**
  (`df -h /e`). MSVC is mentioned as a PC compiler (`docs/tech/cmake.md:10`) but no check shows it is exercised.

## Decisions

| Decision | Options (pros / cons / cost) | Recommendation | Why not the others |
|---|---|---|---|
| **1. How a game project consumes the engine** | **A. FetchContent of the release source archive** (URL + SHA-256), with CMake's own override `FETCHCONTENT_SOURCE_DIR_NNHGE=<local engine>`: tiny game repo, exact pin, upgrade = 2 lines, works on any CI; needs a download on the first configure of each preset and an HTTPS-capable CMake (also inside devkitPro's MSYS2). **B. git submodule**: familiar, easy to patch the engine; needs git and `--recursive`, pulls the whole history (specs, tests), the game must be a git repo. **C. Vendored copy** (`nnhge/` inside the game): offline, self-contained; +5 MB per game, upgrades by replacing a folder, easy to drift by editing it. **D. Installed package** (`find_package`, prebuilt libs per preset): fastest configure; must ship 6 flavours × host ABIs (MinGW, MSVC, GCC versions), export targets, and the data schema programs still compile game sources with the engine's sources; much work for 1.0. | **A by default, generated by `nnh new`**, on top of **one contract**: "the engine works as an `add_subdirectory()`/FetchContent subproject". B and C then work for free with the same contract and are documented in one paragraph each. | B and C are not wrong, they are the same contract; A is the default because a newcomer does not need git skills and the pin is checked by hash (constitution X). D is real work with ABI risk and no gain a newcomer feels; revisit if configure time becomes a complaint. |
| **2. Presets in a game project** | **A. A full `CMakePresets.json` generated by `nnh new`** with the same six names and `build/<preset>` layout; **B. `include` of a presets file shipped with the engine** (the engine is fetched *after* presets are read, so it would need a local SDK path); **C. Only `pc-dev` and `3ds-dev`**. | **A**, same six names, with `FETCHCONTENT_SOURCE_DIR_NNHGE` left to `CMakeUserPresets.json` (git-ignored) for a local engine. | B cannot work with FetchContent (chicken and egg). C would make `nnh run --release` and `NNH_PRESET=pc-debug` behave differently from the engine repo, which the docs and the tool assume everywhere. |
| **3. What marks a game project for `nnh`** | **A. | **5. How `nnh` is distributed** | **A. Prebuilt per OS** (Windows x64 static MinGW, Linux x64 with static libstdc++ built on an older glibc) **plus build-from-source** in the source archive; **B. Source only**; **C. C is maintenance per manager; after the newcomer test, if at all. |
| **6. Where release artifacts are built** | **A. A manual `release.yml`** (`workflow_dispatch`, input = tag) on GitHub-hosted runners, producing a **draft** release; the same steps as scripts in `scripts/release/` so they also run locally/VM 120; **B. Everything local** (PC + VM 120), uploaded with `gh`; **C. Tag-triggered automatic workflow**. | **A**: clean machines, a log anyone can read, free for a public repository, and still manual like today's CI. Versioning and the 1.0 promise** | SemVer, annotated tags `vX.Y.Z`; **stable in 1.x**: game-facing headers in `engine/core/include/nnh/*.hpp` (not `nnh/detail/`), `nnh_add_game()` options and the `nnh::engine` target, preset names, input file formats (Tiled `.tmj` subset, Aseprite JSON, data and strings TOML subsets, `.nnhs` scripts), the save file format (players' SD cards keep them), `nnh` commands, options and exit codes; **not stable**: `nnh/detail/*`, the platform contract (`nnh/platform/*`), converted formats (`.nnhmap`, `.nnhmesh`, NNHD — regenerated at build), the game↔tool wire protocol (same-release rule), environment variables used for testing, exact self-check goldens across versions, ABI. ## Spec breakdown (what the plan turns into)

- **Spec 032 — Game projects outside the repository.** The subproject contract: `nnh_add_game()` and helpers safe from
  any directory (paths and platform through global properties or `include_guard`ed cache variables, not
  directory variables); examples, tests, NNH Link and the `nnh` tool built only when the engine is the top-level
  project (`PROJECT_IS_TOP_LEVEL`, options still overridable); `NNHGE_VERSION*` CMake variables; a documented
  FetchContent recipe; `nnh` finds a game project (`nnh.toml`) as well as the engine repo and passes the host
  compiler to 3DS configures like `dkp.sh`; a consumer fixture project built by `ctest` (PC) and by the checklist
  (3DS). New decision D55.
- **Spec 033 — `nnh new`, `nnh doctor`, `nnh --version` and the newcomer docs.** Templates embedded in `nnh`; the
  generated project builds on PC and 3DS out of the box and passes its own `tests/smoke.nnhs`; `doctor` checks and
  report format; a new "Your first game" guide and a rewritten getting-started. D56.
- **Spec 034 — Versions, stability and releases** (lean path: mostly process, CI and docs). `<nnh/version.hpp>`,
  version 1.0.0 in CMake, the stability page, `NNH_DEPRECATED`, `CHANGELOG.md`, `scripts/release/`, `release.yml`, the
  release checklist page, devkitPro container pinned by digest, `SHA256SUMS`, the build-time injection of the engine
  archive's URL and hash into release `nnh` binaries. D57.

## Steps

Precondition for every implementation step: one implementation at a time, in a worktree, never on `main`
(maintainer's rule); at least **10 GB free on `E:`** (13 GB today: a consumer fixture adds one more engine build per
preset) and VM 120's disk checked with `df -h` before Linux runs.

### 0. Finish the 1.0 features
- Do: implement spec 031 (approved) and set spec 030's console bench budgets.
- Touches: as their plans say.
- Done when: `specs/README.md` shows 030 budgets set and 031 implemented; merged to `main`.
- Verify: `ctest --preset pc-debug`; 031's console run; ROADMAP ticks.

### 1. Spike: build an out-of-tree game against the current engine (throwaway, outside the repo)
- Do: in a `mktemp -d` folder, a 10-line game project that (a) `add_subdirectory()`s a `git archive` of `main` and
  (b) uses FetchContent with `URL file://…/nnhge.tar.gz` + `URL_HASH`; configure and build `pc-debug` on Windows and
  `3ds-dev` through devkitPro's MSYS2 (with and without `NNH_HOST_CXX`), and `pc-debug` on VM 120. Also check: an
  empty `FETCHCONTENT_SOURCE_DIR_NNHGE` falls back to the download; an `https://github.com/...` download works from
  devkitPro's MSYS2 CMake; configure time and a one-file rebuild time of the out-of-tree game. Delete the folder at the
  end.
- Touches: nothing in the repo.
- Done when: a findings list exists (expected: the directory variables listed in "Current state", `NNH_PLATFORM`
  scope, examples/tests/apps built, host compiler in cross presets, anything else) and is pasted into spec 032's
  draft under "Context".
- Verify: the build logs of the four configurations; timings recorded.

### 2. Draft specs 032, 033 and 034 and get them approved

### 4. Spec 033: plan, tasks, implementation
- Do: `nnh new <name> [--title] [--author] [--engine <path>]` writes the template below; `nnh doctor [--online]
  [--console <ip>]`; `nnh --version`. Templates live in `tools/nnh/templates/game/` and are embedded at build time
  (`cmake/nnh_embed.cmake`). Release builds of `nnh` get the engine archive URL and SHA-256 as build-time definitions
  (step 6); a `nnh` built from a checkout generates projects pointing at that checkout through `CMakeUserPresets.json`.
- Generated project (one template):
  - `CMakeLists.txt`: `cmake_minimum_required(3.25)`, `project(<name>)`, FetchContent of the engine, `nnh_add_game(<name>
    SOURCES src/main.cpp src/play_scene.cpp ASSETS assets TITLE … AUTHOR … VERSION 0.1.0 CIA UNIQUE_ID <random in
    0x00300–0xF7FFF>)`, no `ICON` (the default icon), a comment for each optional keyword;
  - `CMakePresets.json` (decision 2), `nnh.toml`, `.gitignore` (build/, `CMakeUserPresets.json`, `*.3dsx`, `*.cia`,
    `*.smdh`, `*.elf`), `.gitattributes` (assets binary);
  - `src/main.cpp` + one scene: a sprite moved by the Circle Pad, text on both screens, a sound on A, START quits;
  - `assets/art/player.png`, `assets/sfx/blip.wav` made by the project (engine-made, zlib), `tests/smoke.nnhs`;
  - `README.md`: build/run commands, links to the docs **at the engine's tag**, and a licence note: the game's
    licence is the author's choice; NNHGE (zlib) and its vendored code require no notice in a shipped game (to confirm
    for each vendored library in `docs/tech/third-party.md`); no Nintendo SDK or copyrighted assets.
  - No `LICENSE` file is generated.
- `doctor` checks, one line each (`ok`/`warn`/`FAIL` + a fix command or link), grouped "Simulator", "3DS", "Console",
  "This project", then a one-line verdict per group; exit 0 when nothing required fails:
  - nnh version and OS; CMake ≥ 3.25; Ninja; a C++20 host compiler (`g++`/`clang++`/`cl`, version);
  - SDL3: system package found, or (with `--online`) the pinned download reachable through CMake (catches the
    Windows CA problem); on Linux, `pkg-config` for the SDL build dependencies;
  - devkitPro: `DEVKITPRO` set, `3DS.cmake`, devkitARM and libctru/citro2d/citro3d present (versions); on Windows its
    MSYS2 bash, CMake and Ninja inside it, and a host compiler to pass as `NNH_HOST_CXX`;
  - optional: ccache, git, Azahar;
  - console (`--console <ip>` or discovery like `nnh run`): found / not found ("open the Homebrew Launcher and press
    Y"); LAN only, as spec 010 FR-7;
  - project (inside one): `nnh.toml` engine version = `nnh`'s version (else warn: the wire protocol must match), free
    disk space in the project folder.
- Touches: `tools/nnh/src/` (new `commands/new.cpp`, `commands/doctor.cpp`, `cli.*`), `tools/nnh/templates/`,
  `tools/nnh/CMakeLists.txt`, docs (`docs/guides/your-first-game.md` new, `getting-started.md`, `nnh-tool.md`,

## Risks and reversal

- **Making the CMake helpers subproject-safe changes the in-repo build** (renamed variables, gated subdirectories). Signal:
  `ctest` failures, an example missing in `nnh_games.txt`, a changed self-check golden or `hello` size, slower
  configure. Reversal: the work is on a worktree branch; revert the merge commit. Works with new data: yes (build
  files only).
- **FetchContent downloads fail on newcomer machines** (Windows CMake without CA certificates, devkitPro's MSYS2 CMake,
  proxies). Signal: step 1, `doctor --online`, newcomer test. Fallback without code: `FETCHCONTENT_SOURCE_DIR_NNHGE`
  to an unpacked archive (documented). If common: reconsider decision 1C as an `nnh new --vendor` option.
- **A wrong URL or hash injected into release `nnh` binaries**: every `nnh new` project fails at configure. Signal: the
  checklist's "prebuilt `nnh new`" line on the draft. Reversal: the release is still a draft; fix and rerun the
  workflow. After publishing: a `.1` release (never replace assets).
- **Tags and published releases are public and effectively irreversible** (projects pin the archive hash). Steps 6 and
  8 need the maintainer's explicit OK before `git push --tags` and before "Publish". A wrong tag before publishing can
  be deleted; after, only superseded.
- **Wire-protocol mismatch** between a user's `nnh` and their project's engine version (hello `kVersion`). Signal:
  `nnh run` refuses the game. Mitigation: `doctor` and `nnh run` print both versions and the fix (use the `nnh` of the
  same release).
- **devkitPro moves on** ("latest only"): a new devkitARM breaks the 3DS build after release. Signal: user reports,
  `doctor` shows versions. Mitigation: tested versions in release notes; the release workflow pins the container by
  digest; fixes in a patch release.
- **The Linux `nnh` does not start on older distributions** (glibc). Signal: the Ubuntu 22.04 check. Mitigation: build on
  `ubuntu-22.04`, static libstdc++/libgcc.
- **Windows SmartScreen warns on an unsigned `nnh.exe`.** Mitigation: README says so and shows how to check
  `SHA256SUMS`; signing stays a non-goal.
- **Over-promising API stability.** Mitigation: decision 7b and the explicit not-stable list.
- **Merge conflicts with spec 031**, which also changes `nnh` (D53/D54). Mitigation: 032–034 implemented after 031 is
  merged (step 0).
- **Disk space on `E:`** (13 GB free): consumer and template builds add engine builds per preset. Signal: build errors
  on write. Mitigation: precondition ≥ 10 GB; clean `build/` folders of finished worktrees.
