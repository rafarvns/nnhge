## Design

### Overview

```
assets/levels/level1.tmj ─┐
```

### Decision D26 — how tile layers are drawn (the key risk)

**Numbers we start from** (Old 3DS XL, Release, `examples/sprites` benchmark): ~1300 sprites of 16×16 at 60 Hz,
i.e. ≈ 12.8 µs of a 16.7 ms frame per sprite *all-in* (game update, `gfx::draw` recording an 80-byte
`DrawCommand`, the layer sort, `DrawItem2D` build with a texture lookup, `C2D_DrawImage`). The GPU is not the
limit (1300 × 256 px ≈ 0.33 Mpx per frame). Visible cells per map layer, worst case (camera not aligned):

| Tile size | Top screen 400×240 | Bottom 320×240 |
|-----------|--------------------|----------------|
| 8×8 | 51 × 31 = 1581 | 41 × 31 = 1271 |
| 16×16 | 26 × 16 = 416 | 21 × 16 = 336 |
| 32×32 | 14 × 9 = 126 | 11 × 9 = 99 |

As plain sprites, three 16×16 layers (1248 draws) would use the whole frame and more than half of the default
`max_draws` (2048, ~136 B each). Three options were evaluated:

| | A. Tiles as sprites | B. Pre-rendered chunks (render to texture) | **C. Tile batches (chosen)** |
|---|---|---|---|
| CPU per frame | ~12 µs/tile → ~5 ms per 16×16 layer | ~6 quads per layer, but a new row/column of chunks costs 256–768 tile draws in one frame (spikes) | one command per (layer, tileset); per tile ≈ cell read + table lookup + quad write (~0.2 µs) + citro2d quad (est. 2–4 µs) → **est. 1–1.8 ms per full 16×16 layer** |
| Memory | 136 B × visible tiles in the draw list | 256×256 RGBA8 chunk = 256 KB; ≤ 6 visible per layer → **1.5 MB VRAM per layer** (4 layers = all 6 MB VRAM; RGBA5551 halves it) | 12 B per quad in one 19 KB scratch (one batch at a time) + citro2d vertices (~192 B per quad, `Linear`) for `max_tiles` |
| Animated tiles, `set_tile` | free | invalidate and re-render chunks | free (read at submit) |
| Contract | none | render targets on both platforms (new texture kind, VRAM management) | one function `draw_tiles` |
| Complexity | none | high (cache, eviction, spikes, two RTT backends) | low |

**Chosen: C, tile batches.** `gfx::draw_tilemap` records *one* command per (map layer, tileset) into the frame's
draw list, sorted by draw layer like sprites (so "same layer = call order" holds and a player sprite fits between
background and foreground). At submit, when the sorted pass reaches a tile command, core flushes the sprites
before it (`draw_2d`), expands the visible cells into a compact quad array and calls the new contract function
`draw_tiles` once for that batch; then it continues. The platform maps quads to the GPU in a tight loop: no
rotation, no pivot, no per-tile texture lookup, one tint per batch.

- **Camera, parallax, offset, ignore_camera**: computed once per batch at submit (the camera at the *end* of the
  frame, like sprites). The layer's screen origin is snapped to whole pixels **once**, so tiles are exact
  multiples of the tile size from it: no seams, no per-tile rounding, PC and 3DS agree.
- **Flips** (incl. diagonal) travel as 3 bits per quad; the platform maps them (3DS: UV corners / citro2d's
  rotated sub-texture rule; PC: `SDL_RenderTextureRotated` 90° + flip). Diagonal flips need square tiles (checked).
- **Opacity**: layer opacity × draw opacity → the batch's tint alpha (one tint per batch).
- **Nearest filtering**: textures already use it; whole-pixel positions + exact UVs → no bleeding.
- **Stereo (M8)**: a batch carries its draw layer like a sprite, so per-layer depth works the same way.

Target, to be **measured at the stage-3 gate** on an Old 3DS (benchmark mode of the example): at least **4 full
layers of 16×16 tiles on the top screen plus 300 sprites at 60 Hz**. If one full layer costs more than 2.5 ms,
the fallback order is: write citro2d's vertices in a tighter loop of our own (same contract); then option B for
static background layers only (a follow-up spec). AC-4 reports the measured number.

### Decision D27 — the converter is a host C++ tool, `nnh-assetc`

What the repo does today: header checks are CMake `-P` scripts (`nnh_check_image/sound.cmake`), PNGs are converted
by devkitPro's prebuilt `tex3ds`, and decisions D6/D10 reserve a C++ `assetc` for heavier conversions. A Tiled
map is one: CMake's `string(JSON)` re-parses the whole document for every value (quadratic on a 100 k-cell layer)
and CMake cannot write binary files; Python is not a build dependency of games (D23 avoided it on purpose). So:

- **`tools/assetc/`**, program `nnh-assetc`, C++20 with the engine's rules (no exceptions/RTTI), first command
  `nnh-assetc map <in.tmj> <out.nnhmap> --assets <assets root> --depfile <file.d>`. Its own small bounded JSON
  reader (no dependency). It shares the binary format and the validator with core
  (`engine/core/src/tilemap/map_format.hpp`, `map_validate.cpp`, `core/crc32.cpp`: pure files with no engine
  includes) and validates every file it writes with the same code the console runs.
- **PC presets**: a normal target in the same build (custom commands depend on it).
- **3DS presets** (cross builds): `cmake/nnh_host_tools.cmake` builds it for the host with
  `ExternalProject_Add` and the host compiler `NNH_HOST_CXX` (found on the PATH; `scripts/dkp.sh` passes Git
  Bash's compiler into devkitPro's MSYS2, which has none). Override with `-DNNH_ASSETC=<path>` (a prebuilt
  `nnh-assetc`), like `NNH_MAKEROM`. Only configured when a game's `ASSETS` contain a `.tmj` (XI).
- **Incremental** (III): one custom command per map; `DEPFILE` lists the `.tsj` files and tileset PNGs it read, so
  editing a shared tileset reconverts exactly the maps that use it. A content-hash cache (D6's idea) is not needed.

```cpp
// <nnh/collision.hpp> — plain functions on values; includes only <nnh/math.hpp>.
namespace nnh::collision {

bool overlaps(Rect a, Rect b);              // shared area > 0 (touching edges don't overlap)
bool contains(Rect r, Vec2 p);              // x <= p.x < x + w, y <= p.y < y + h
Rect intersection(Rect a, Rect b);          // {} (w = h = 0) when they don't overlap
Vec2 separation(Rect a, Rect b);            // smallest move of `a` that ends the overlap, {} if none

enum class Cell : std::uint8_t { Empty, Solid, OneWay };   // OneWay: solid only from above

/// A solid grid the game describes; no ownership, no tilemap needed.
struct Grid {
    Vec2 origin{};                          // world position of cell (0, 0)'s top-left corner
    float cell_w = 16, cell_h = 16;
    int width = 0, height = 0;              // cells
    Cell outside = Cell::Empty;             // beyond the edges (Solid walls the level in)
    const Cell* cells = nullptr;            // row-major width * height, used when set (added in stage 1)
    Cell (*cell)(const void* context, int x, int y) = nullptr;   // called only inside the grid
    const void* context = nullptr;
};
/// A grid over a row-major array the game owns (width * height cells).
Grid grid_view(const Cell* cells, int width, int height, float cell_w, float cell_h, Vec2 origin = {});

struct Sides { bool left = false, right = false, ceiling = false, floor = false; };
struct MoveOptions { bool drop_through = false; };          // ignore one-way cells (player pressed down)
struct MoveResult { Vec2 position; Vec2 moved; Sides touching; };

/// Moves `box` by `delta`: x first, then y, stopping at the first solid cell edge on each axis (sliding along
/// the other); scans every cell in between, so no speed tunnels. One-way cells stop only a downward move whose
/// bottom started at or above their top. Cells the box already overlaps are ignored (it can get out). No allocation.
MoveResult move(const Grid& grid, Rect box, Vec2 delta, const MoveOptions& options = {});
Sides contacts(const Grid& grid, Rect box);                  // sides flush against solid (floor: also one-way)
struct CellHit { int x, y; Cell kind; };
int cells_touching(const Grid& grid, Rect box, CellHit* out, int capacity);   // non-empty cells; returns total
}
```

`AppConfig::gfx` gains **`max_tiles`** (tile quads per frame, both screens; default **0**: games without maps pay
nothing; on 3DS each one reserves a citro2d quad, ~192 B `Linear`). `gfx::Stats` gains `tiles_last_frame`,
`max_tiles`, `dropped_tiles`; the debug overlay shows them. Over the limit: assert (Debug/Development), drop and
one warning per frame (Release), like draws.

**Dependency direction** (XI): `collision` depends on `math` only; `tilemap` uses `collision`'s value types
(`Cell`, `Grid`) so `collision::move(map.collision_grid(), …)` works, but never calls it; `gfx` knows a tile batch
only as `{function pointer, source}` (it does not include tilemap), so a game could later feed its own grids.

**Collision rule (FR-7)**: a cell is `Solid` if any tile layer with `collision` set has a non-empty tile there, or
any layer's tile there is marked solid; otherwise `OneWay` if any tile there is one-way; otherwise `Empty`. Only
layers that can contribute (collision layers, or layers holding a solid/one-way tile — a bitmask kept up to date
by `set_tile`/`set_tile_collision`) are visited.

**Parallax (FR-3)**, matching Tiled's preview (it scrolls around the view's centre and the map's parallax origin
`po`): with camera top-left `c`, screen size `s`, layer offset `o` and factor `p`,
`screen = world + o + (c + s/2 − po)·(1 − p) − c`; `p = 1` is a normal layer, `p = 0` stays fixed on screen.
`ignore_camera` uses `c = 0`. Unit tested and checked once against Tiled's preview (example level).

**Animated tiles: included** (spec open question: "if cheap"). Tiled's tile animations become a per-map table
(≤ 256 animated tiles, ≤ 32 frames each, ≤ 4096 frames in total). At submit, each batch resolves the current
frame of each animation once (≤ 256 small loops) into a stack table; a tile whose flag byte says "animated" reads
its frame from it — one branch per tile, no per-cell state, collision uses the base tile. Clock:
`animation_time`, by default `frame_count()` × 1/60 s, so PC and 3DS show the same frame on the same frame number
(FR-10). Cost: ≤ 4 B per frame + 4 B per animation of map memory. Isolated in its own stage; can be cut without
touching the rest.

### Binary format `.nnhmap` (version 1) and in-memory layout

Little-endian, every section 4-byte aligned, all offsets relative to the file start and checked against its size.
The same layout is the in-memory map (one block, sections sized by *capacities*), so a loaded map and a map built
in code are literally the same data and every query is shared.

| Section | Entry | Size |
|---------|-------|------|
| header | magic `NNHM`, version, file size, CRC-32 of the rest, map w/h, tile w/h, parallax origin, map property range, counts **and capacities**, section offsets, runtime collision-layer mask (stage 2) | 128 B |
| tilesets | first id, tile count, tile w/h, margin, spacing, columns, image size, image asset name (string) | 24 B each |
| tile table | per tile id: source x/y in its tileset (u16 ×2, so no divide at draw: the ARM11 has none) + flags byte (collision 2 bits, animated, has properties) | 5 B per tile + 1 |
| tile properties | sparse: tile id → property range | 6 B per tile with properties |
| animations | tile id, first frame, frame count, total duration; frames: tile id + ms | 8 B + 4 B per frame |
| tile layers | name, offset, parallax, opacity, flags, property range, cells offset, tilesets-used mask | 40 B each |
| cells | u16 per cell, row-major: bits 0–12 tile id (0 empty), 13 diagonal, 14 flip y, 15 flip x | 2 B × w × h per layer |
| object layers | name, property range, first object, count | 12 B each |
| objects | id, name, type, shape, x, y, w, h, object layer, property range | 36 B each |
| properties | name, type, value (bool/int/float bits/string offset) | 12 B each |
| strings | NUL-terminated UTF-8, each ≤ 255 bytes | as written |

**Limits** (checked by the converter *and* by the loader/builder): map 1–1024 × 1–1024 cells; tile size 8–64 px
(square or not); ≤ 16 tile layers, ≤ 8 tilesets, ≤ 8191 tile ids in total, ≤ 16 object layers, ≤ 4096 objects,
≤ 16 384 properties, ≤ 64 KiB of strings, animations as above; **total cells of all layers ≤ 4 Mi (8 MiB)** — see
the memory note below. Tileset images obey the texture rules (power of two, 8–1024) through their own asset step.

**Memory of a map** (heap, tag `tilemap`; tileset textures are separate, `Linear`, tag `textures`):

```
bytes ≈ 128 + 24·tilesets + 5·(tile_ids + 1) + 6·tiles_with_properties + 8·animations + 4·animation_frames
      + Σ_tile_layers (40 + 2·width·height) + 12·object_layers + 36·objects + 12·properties + string_bytes
```

| Map | Cost |
|-----|------|
| Example level: 240×30, 3 layers, 1 tileset of 128 tiles, 40 objects, 60 properties, 1 KB strings | 43.2 KB + 0.6 + 1.4 + 0.7 + 1 ≈ **47 KB** |
| Large: 512×512, 4 layers, 2 tilesets (1024 ids) | 2 MiB cells + 5 KB ≈ **2.0 MiB** |
| Spec's worst case: 16 layers × 1024×1024 | **32 MiB of cells** — does not fit next to a game in the Old 3DS's ~64 MB |

So the spec's per-dimension limits hold, with one extra cap on the *total*: 4 Mi cells (8 MiB), e.g. 4 full
1024×1024 layers or 16 layers of 512×512 (**to confirm by the maintainer**). Loading peaks at file + map (the file
is read into a temporary `AssetData`, validated, then copied into the map's block with its extra capacity).
Tileset textures usually cost more than the map: a 256×256 RGBA8 sheet is 256 KB of `Linear`.

**Per frame** (only when drawing maps): batch records 64 × ~48 B in the draw list's side table (3 KB, `gfx`); one
quad scratch of 1600 × 12 B = 19 KB (`gfx`; the worst visible layer is 1581 quads of 8×8, and quads are consumed
synchronously by the platform, so one batch at a time suffices); on 3DS citro2d's vertex buffer grows by
`max_tiles` quads (~192 B each: 2048 tiles ≈ 384 KB `Linear`, to be measured).

#### Stage 2 refinements (2026-11-21, implemented)

Found while building maps in code; the exact layout is `engine/core/src/tilemap/map_format.hpp` and the exact memory
formula is in [tilemap.md](../../docs/api/tilemap.md#memory).

- **Header 128 B, not 96**: a map edited in place needs each section's *capacity* next to its count (files write
  capacity = count; the loader adds `LoadTilemapOptions` extras), plus the section offsets (from the capacities,
  checked by the validator) and a runtime bit mask of layers that can collide (recomputed on load).
- **Tileset entry**: no tile size of its own (tiles use the map's; the converter refuses others), and it carries
  the texture's handle {slot, generation} at run time, so a destroyed texture is detected (stale = skipped).
- **Tile table**: two arrays (4 B source per id, then 1 B flags per id) to keep entries aligned; still 5 B per id.
- **Objects carry their object layer**; object layer entries keep a count but no `first`: objects stay in creation
  order, so the index `add_object` returns never changes.
- **Properties**: each owner's range is kept contiguous by inserting (shifting later entries and ranges). The
  tile-property table's capacity is `min(max_properties, max_tile_ids)`.
- **API additions** (all additive): `TilemapDesc::max_tile_ids` (256; the tile table must be sized at creation),
  `ObjectDesc::id` (0 = automatic; Tiled ids must survive for the code-vs-file test), `PropertyOwner::map()`,
  `tile_layer(i)`, `object_layer(i)`, `tile(id)`, `object(i)`, `Tilemap::tile_id_count()`, the layer getters the
  sketch called "+ matching getters" (`layer_offset` … `layer_collision`), `Tile::operator==`.

#### Stage 3 refinements (2026-11-21, implemented)

Found while building the drawing path; the exact code is `engine/core/src/gfx/tile_batches.*`,
`engine/core/src/tilemap/{visible_range,tile_expand,map_draw}.*` and the contract `nnh/platform/video.hpp`.

- **`TileQuad2D::orient` bit order**: diagonal = 1, flip y = 2, flip x = 4 (`kTileOrient*`), so the orientation is
  the cell's bits 13–15 shifted down once (`cell >> 13`, checked by `static_assert`) instead of three tests per
  tile. The quad is **10 bytes** (no padding needed; `static_assert(sizeof <= 12)`): the scratch is 16 KB.
- **Public API additions** (additive): `Tilemap::set_parallax_origin(Vec2)` / `parallax_origin()` — the formula uses
  the map's parallax origin, and a map built in code needs a way to set what Tiled maps carry (FR-0).
  `TilemapDrawOptions` has no `animation_time` yet: stage 6 adds it with animated tiles.
- **Visibility**: a hidden map layer draws nothing even when named by `map_layer`; opacity 0 records nothing.
- **Batches per frame**: 64 (`kMaxTileBatches`); past it the batch is dropped with an assert. Each batch also takes
  one draw-list command (it keeps its place among the sprites), so it counts in `max_draws`.
- **Split points**: `DrawCommand` gained `tile_batch` (an `int16` in existing padding: the command's size is
  unchanged); `DrawList::build()` writes `TileSplit{items before it, batch}` instead of an item.
- **Memory**: records and scratch are allocated only when `max_tiles > 0` (≈ 20 KB on PC, less on 3DS).
- **Asserts inside the frame's submit** (tiles over `max_tiles`) happen after the frame's lists are cleared: the
  crash leaves the frame open and `shutdown()` submits it again, which must not assert twice.
- **Stats**: `dropped_tiles` counts since `init()` like `dropped_draws`; the overlay's tiles line appears only when
  `max_tiles > 0` (XI).
- **PC read-back test** lives in its own PC-only file `tests/platform_conformance/test_draw_tiles_pc.cpp` (linked
  into `nnh_conformance_pc` with SDL3): `test_contract.cpp` uses only the contract, which cannot read pixels.
- **Example**: besides the files listed in tasks, `art.hpp` (tile ids), `bonus.cpp` (play loop: camera, coins,
  HUD), `player.cpp` and `flips.cpp`; SELECT cycles bonus → bench → flips. The bench goes up to 12 full layers and

#### Stage 4 refinements (2026-11-21, implemented)

Found while writing the validator and the loader; the exact code is `engine/core/src/tilemap/map_validate*.{hpp,cpp}`,
`map_copy.{hpp,cpp}` and `map_load.cpp`.

- **Validator split in two files** (`map_validate.cpp`: header, layout, strings, tilesets, tile table;
  `map_validate_content.cpp`: layers and cells, objects, properties; internal `map_validate_parts.hpp`) to stay
  near the 200-line aim. It returns `{MapProblem, reason}` (`Damaged` → `Corrupted`, `NewerVersion` →
  `Unsupported`, `OverLimit` → `LimitReached`), reads through `memcpy` (any alignment) and is pure, so the converter
  can use it. Strict where the converter can be: capacities ≥ counts and offsets equal to the layout of those
  capacities, tile sources equal to what the tileset gives, the has-properties flag matching the sorted tile-property
  table, every property owned by exactly one range, finite floats, opacity 0..1, point objects with no size, object
  ids 1..2^31−1, each layer's tilesets mask covering the tilesets its cells use. Runtime fields are ignored.
  **Animated tiles** (any animation, frame or `animated` flag) are refused as `NewerVersion` until stage 6 adds them.
- **Copy step as its own pure file** (`map_copy.{hpp,cpp}`, not in the plan's file list): `loaded_capacities` (file
  capacities + extras; each extra checked against its limit before adding, so no overflow; the tile-property table
  grows by `extra_properties`, up to the tile ids) and `copy_map` (only used entries are copied, so the extra room is
  zero; layer cell offsets set for the new layout; texture handles −1; collision-layer mask recomputed). The fuzz
  target uses it through `detail::tilemap_from_file` without the engine running.
- **Texture ownership**: a loaded map owns its tileset textures. Header byte `reserved1` became `owned_textures`
  (runtime bit per tileset; `Tilemap::reset` frees them through `detail::release_map_textures`); tilesets with the
  same image share one texture (only the first owns it); `TextureAccess::release` hands a texture over without
  freeing it. A tileset image whose size differs from the one recorded at conversion is `Corrupted`.
- **`LoadTilemapOptions`** as sketched; object layers and tilesets cannot be added to a loaded map (no extras for
  them).
- **Fuzz target** body in its own file `tests/fuzz/fuzz_tilemap.cpp` (in `nnh_fuzz_targets`). It validates the
  input as is, then with the header's size and CRC fixed (otherwise nearly every mutant dies at the CRC), and on
  an accepted map runs every query, the tile expansion of each layer × tileset for a 400×240 view, `collision::move`
  and edits into extra room. Mini-fuzz: 2 × 4000 mutants of the sample and minimal maps; more than 100 are
  accepted, so the deep path runs.
- **Tests' file writer**: `tests/tilemap/map_file.{hpp,cpp}` builds `.nnhmap` buffers with the pure layout helpers
  (`sample()`, `minimal()`) or writes a map built in code (`from_map()`), and `seal()`s damaged ones.

Found while writing the converter; the exact code is `tools/assetc/src/` and `cmake/nnh_assets.cmake`.

- **Files differ from the list below** (one concept each, all ≤ 215 lines): the JSON reader is `json.{hpp,cpp}`
  (document and `Ref` views), `json_parse.cpp` (the parser) and `json_string.{hpp,cpp}` (one string literal:

  writer), `convert_context.hpp` (files, assets root, dependencies, first problem), `convert.{hpp,cpp}` (one whole
  conversion, no disk writes), `files.{hpp,cpp}` (`FileSource`: disk, or memory for tests and fuzzing) and

  `tools/assetc/tests/fuzz_assetc.{hpp,cpp}` (library `nnh_assetc_fuzz`).
- **JSON limits**: document ≤ 64 MiB, nesting ≤ 32, **≤ 8 Mi values** (a full 4-layer 1024×1024 map has 4 Mi cells),
  numbers ≤ 64 characters and finite; strict RFC 8259 (no BOM, comments, trailing commas); strings decoded into one
  pool, values in one array (`Limits` lowers them in tests). Errors give `line L, column C`.
- **What becomes what**: tile properties `solid`/`one_way` and the layer property `collision` (bools) become the
  collision flags and are **not** kept as properties (a map built in code sets the flags, not properties; both
  true on a tile is refused). Tilesets get NNHGE's consecutive ids in first-gid order (gaps in Tiled's gids are fine;
  two tilesets with the same first gid are refused). A point drops any size. An object's type is `type`, or `class`
  when `type` is empty. Tile-level editor data (`probability`, collision shapes `objectgroup`, `type`) is ignored.
- **Refused besides the plan's list**: `.tsx` tilesets ("export the tileset as JSON"), tile offsets, layer tint
  colours, object templates, rotated objects, the hexagonal 120° gid bit, duplicate property names, a `.tmj` next to
  a `.nnhmap` of the same name (configure error). Animated tiles are refused until stage 6 (T6.3).
- **Margin**: NNHGE keeps the margin on every side (`tiles_along`, stage 2); Tiled counts columns with the margin
  once. A tileset whose last column touches the image's right edge is refused with the columns message instead of
  being converted differently.
- **Tileset files may sit anywhere** (they are not packed); only images must be PNGs inside the assets folder. The
  converter reads only a PNG's 24-byte header (the image itself goes through its own asset step).
- **Depfile paths are relative to the step's working directory**: devkitPro's MSYS CMake read the native tool's
  absolute `E:/...` paths as relative ones (prefixing the build folder), so on 3DS every map reconverted on every
  build. Found with `ninja -d explain`; `relative_path()` + a CLI test.
- **Build wiring**: the top-level `CMakeLists.txt` sets up host tools and calls `enable_testing()` before
  `examples/` (games ask for the program at configure time). `nnh_asset_index.cmake` is unchanged: `nnh_assets.cmake`
  now hands it the output names (`nnh_asset_output_name()`, tested by `asset_index_names_maps_by_their_output`).
  Map depfiles go to `<game build dir>/nnh_maps/`, outside the packed folder.
- **Fixtures**: the PNGs are generated by `tests/data/maps/make_fixtures.py` (standard library only); the 4097-object
  map is written by `tests/CMakeLists.txt` at configure time instead of being committed. `map_convert_accepts_good`
  checks the good map converts; 21 bad maps each have a `rejects`/`explains` pair (the plan's list plus compressed
  data). T5.9 converts `good.tmj` at build time (target `nnh_test_maps`) into `build/<preset>/tests/maps/`.
- **Version** stays 0.1.0 (the `map` command is the tool's first; maps depend on the program file anyway).

### Platform work

```cpp
// nnh/platform/video.hpp additions
struct TileQuad2D {                 // 12 bytes
    std::int16_t x, y;              // destination top-left, whole screen pixels
    std::uint16_t src_x, src_y;     // source top-left in the texture
    std::uint8_t orient;            // bit 0 flip x, bit 1 flip y, bit 2 diagonal (applied first, as Tiled)
};
struct TileBatch2D {
    TextureHandle texture; int tile_w, tile_h;
    Color color;                    // tint; alpha = opacity
    std::uint8_t layer;             // 0..15, as DrawItem2D
    const TileQuad2D* quads; int count;
};
/// Draws same-size tiles of one texture on `screen`, in order, clipped to it. Called between draw_2d() calls of
/// a pass. Must not allocate and must consume `quads` before returning (core reuses the buffer).
void draw_tiles(Screen screen, const TileBatch2D& batch);
```

- **3ds** (`draw_tiles_3ds.cpp`): `1/width`, `1/height` once per batch; per quad a `Tex3DS_SubTexture` and
  `C2D_DrawImage` with angle 0, one shared `C2D_ImageTint` only when the color is not white; flips by negative
  size, diagonal by the rotated sub-texture (`top < bottom`, tex3ds' rule) plus a flip. `app_3ds.cpp` sizes
  `C2D_Init` with `max_tiles`. Measured at the stage-3 gate; the tighter loop is the first fallback.
- **pc** (`draw_tiles_pc.cpp`): `SDL_RenderTexture` per quad (SDL batches them), `SDL_RenderTextureRotated` (90°
  + flip) for diagonal ones; one color/alpha mod per batch.
- **fake**: records each batch (texture, size, color, layer, count) and the first quads, and the call order
  among `draw_2d` calls (`calls` string gains `t`/`b`), so tests check interleaving with sprites.

- Player: run, jump, drop through planks (down + jump), camera follows with clamping to the map; coins collected
  by `collision::overlaps`, removed with a flag, `CoinCollected` published, HUD on the bottom screen.
- Modes: `PLATFORMER_DEMO=bench` (SELECT on the console) — N full-screen tile layers of 16×16 scrolling
  diagonally plus M sprites, L/R and Y/X change N and M, the overlay shows FPS, draws and tiles (AC-4);
  `PLATFORMER_DEMO=replay` — a scripted 600-frame input, logs a checksum of the player's positions and touched
  sides every 60 frames so PC and console logs can be compared (FR-10); `PLATFORMER_DEMO=bonus|flips` for

## Risks and alternatives

- **Tile cost on the Old 3DS is an estimate** (2–4 µs per citro2d quad). Gate at the end of stage 3 with the
  benchmark before the loader and converter are built on top; fallbacks in D26 (own vertex loop, then cached
  chunks for static layers).
- **citro2d's quad budget is shared**: `C2D_Init` reserves `max_draws + max_tiles + debug` objects (~192 B each,
  `Linear`). A game with 4 layers on both screens needs `max_tiles` ≈ 2048 (~384 KB). Documented in gfx.md; core
  counts quads on every platform so the simulator drops/asserts exactly like the console (D4).
- **Host compiler inside devkitPro's MSYS2** (Windows) and in the `devkitpro/devkitarm` CI image: first task of
  the plan is a spike proving the ExternalProject build there; fallback `-DNNH_ASSETC=<path>` to a PC build's
  `nnh-assetc` (documented). A game without maps never needs it.
- **Diagonal flips on 3DS** rely on citro2d's rotated sub-texture convention: checked with the example's flip
  row on the console against the PC screenshot (the PC side is verified by pixel read-back).
- **Float determinism (FR-10)**: x86-64 SSE and ARM11 VFP give the same IEEE results for +, −, ×, ÷ without FP
  contraction (`CMAKE_CXX_EXTENSIONS OFF` → `-std=c++20`, contraction off in GCC). Collision only adds, compares
  and snaps to cell edges. Checked by the replay checksum on hardware.
- **Tiled's parallax formula** (centre-based) must be matched exactly; one manual comparison with Tiled's preview.
- **Rejected alternatives**: runtime JSON parsing on the console (slow, big, an external parser on the device);
  CMake-script converter (quadratic JSON access, no binary output); Python converter (new build dependency for
  every game); a JSON library (dependency, not bounded to our rules); chunk caching as the primary path (VRAM,
  spikes, complexity); tiles counted in `max_draws` (136 B of core memory per tile slot for nothing).

## Questions for the maintainer (answered 2026-11-21: all as proposed)

1. **Total cells cap**: the spec's limits allow 16 × 1024×1024 layers = 32 MiB of cells. Proposed: keep the
   per-dimension limits and cap the total at 4 Mi cells (8 MiB) per map. **Yes.**
2. **`max_tiles` default 0** (XI: no cost for games without maps; `draw_tilemap` asserts with the fix in the
   message) versus a default like 2048 (~384 KB of `Linear` on 3DS for every game). Proposed: 0. **Yes, 0.**
3. **Tiled objects beyond rectangles and points** (ellipse, polygon, polyline, tile objects) are refused at build
   time in this spec (the spec lists rectangles and points). OK to refuse, or convert ellipses/tile objects to
   their bounding rectangles? **Refuse.**
4. **Property types `color` and `file`**: proposed `color` → string `#AARRGGBB`, `file` → string (path as written),
   `object` → int (object id); `class` refused. OK? **Yes.**
